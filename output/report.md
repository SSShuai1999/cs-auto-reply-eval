# 客服自动回复质量评估报告

- 评估对象：`data/auto_replies.json`，20 组「用户问题 + 自动回复」
- 评估模式：`mock`（rubric v1，mock 与真实 LLM API 同构）
- 指标与权重：忠实度（不瞎编）（35%）、准确性（30%）、有用性（20%）、语气（15%）

**整体均分 3.92 / 5**（中位数 3.94）——处于「可用但不及格」区间。

**对业务决策的直接回答**（评估结果用于决定是否扩大自动回复覆盖范围）：

> 当前质量**不建议直接扩大覆盖**。忠实度（4.67）说明回复基本不瞎编，底线可用；但有用性仅 2.88，最典型的问题是「只给通用说明、不帮用户实际处理」——这类回复不会引发事故，但会持续消耗用户耐心。建议先修复最差 case 暴露的三类系统性问题（见第三节），复评达标后再扩大。

## 三、最差 3 条 case 及分析

### case_20（总分 3.17）—— 答非所问：用户说'搞不懂流程'，回复把流程原样复述一遍

- **用户问题**：退货流程太复杂了搞半天都不知道怎么操作
- **自动回复**：抱歉给您带来困扰。退货流程一般包括：1.在订单页面点击退货 2.选择退货原因 3.提交申请等待审核 4.按照退货地址寄回商品。如果您在某个环节遇到问题，可以截图发给客服，我们会协助您操作。
- **分项得分**：忠实度 5.0 / 准确性 2.0 / 有用性 1.5 / 语气 3.5
- **人工标注**：用户已经表达了操作困难和不满。自动回复又重复了一遍退货流程——这恰恰是用户说搞不懂的东西。人工回复会问具体卡在哪一步，然后针对性帮忙。自动回复属于'答非所问'。

用户明确表达'退货流程太复杂了搞半天都不知道怎么操作'，诉求是**被带着操作**，而自动回复恰恰把用户说看不懂的同一份流程又复述了一遍——提供的是用户已声明无效的信息，有用性全场最低（1.5）。人工参考的正确做法是追问'卡在哪一步'再针对性指导。

**根因**：回复生成只看'问题主题'（退货流程）而没有识别'消息类型'（抱怨/求助而非询问）。这是意图识别粒度过粗导致的答非所问，属于准确性事故（2.0）。

**改进建议**：在意图分类中增加'抱怨/求助 vs 信息咨询'的区分；对抱怨类消息强制走'追问具体卡点'策略，禁止直接复述通用流程。

### case_11（总分 3.25）—— 自相矛盾：先说'换货=先退货再下单'，又说'发起换货申请'

- **用户问题**：买了两件衣服一件大了一件小了想换尺码
- **自动回复**：您好，换货需要先退货再重新下单选择正确尺码。请分别发起两件商品的换货申请，按照退货地址寄回原商品，我们收到后会发出新尺码的商品。换货运费由买家承担。
- **分项得分**：忠实度 3.5 / 准确性 3.0 / 有用性 3.0 / 语气 3.5
- **人工标注**：用户的问题包含两件不同的商品，需要确认具体信息才能操作。自动回复直接给出了通用流程说明，没有追问具体商品信息来帮用户处理。

同一回复内给出两条互斥的处理路径（'换货需要先退货再重新下单'与'请分别发起两件商品的换货申请'），用户无法判断该走哪条。'换货=先退再买'是模型的无据自创规则，忠实度被扣到 3.5——这是 20 条中唯一的自相矛盾 case。

**根因**：多商品场景（两件衣服一大小）触发了流程拼接，模型把两套话术揉进了一条回复。另外，两件商品分别换什么尺码是处理此事的必要信息，回复没有追问。

**改进建议**：上线前对回复做'内部一致性自检'（同一回复中的流程断言是否互斥）；多商品/多对象场景强制先追问关键信息再给方案。

### case_19（总分 3.3）—— 无据功能断言：'加入购物车，补货时系统会自动提醒您'

- **用户问题**：我要买的那个包什么时候补货
- **自动回复**：您好，商品补货时间不固定，建议您关注商品页面或联系客服询问预计到货时间。您也可以将商品加入购物车，补货时系统会自动提醒您。如果长时间未补货，可以考虑查看类似的替代商品。
- **分项得分**：忠实度 3.5 / 准确性 3.5 / 有用性 2.5 / 语气 3.5
- **人工标注**：用户问的是具体商品的补货时间。自动回复没有查具体商品，给了通用建议。人工回复会实际查询补货计划并主动帮用户设置提醒。

用户问'什么时候补货'，回复未查询具体商品，且声称'加入购物车后系统会自动提醒补货'——这是一个对系统功能的具体断言，若该功能不存在就是典型'瞎编'（忠实度 3.5，并列全场最低）。这类编造在客服场景风险极高：用户会基于不存在的功能产生预期，后续必然投诉。

**根因**：模型用'听起来合理'的行业常见功能填充答案，而非基于已核实的产品能力作答。

**改进建议**：为自动回复接入'产品能力白名单'（已核实的功能/政策库），生成时只允许引用白名单内的功能断言；白名单外的一律降级为'我帮您确认'。

三条最差 case 恰好暴露三类不同性质的问题：**意图识别过粗**（case_20）、**生成一致性缺失**（case_11）、**无据断言**（case_19）。都是系统性问题，修复收益会外溢到全量回复。

## 四、与人工标注的一致性验证

用 `human_ref.json` 的 annotator_notes 验证评估方法是否靠谱：

1. **短板判断一致**：人工标注 13/20 条提到「没有帮用户处理 / 把责任推给用户」类问题；本流水线四指标中有用性均值最低（2.88），两者独立得出同一结论——**缺乏主动处理是该自动回复系统的最大短板**。
2. **词法信号交叉验证**：有用性低分（≤2.5）的 10 条 case 中，8 条同时被「主动处理 vs 推诿」词法检测判定为净推诿（一致率 8/10），说明 judge 的有用性评分有可解释的信号支撑，不是拍脑袋。
3. **最差 case 重合**：流水线总分后 5 名 ['case_01', 'case_02', 'case_11', 'case_19', 'case_20'] 中，case_01（推卸责任）与 case_20（答非所问）也是人工措辞最严厉的两条。
